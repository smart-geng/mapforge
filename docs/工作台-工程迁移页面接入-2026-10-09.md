# 工作台工程迁移页面接入

日期：2026-10-09。接续 [工作台开发交接](交接说明-2026-10-09-工作台接续.md) 第 8 节 P0“工程迁移页面”。本次把已提交的迁移服务内核 `project_transfer.py` 接到本机 HTTP 和页面；迁移内核、默认转换、评分阈值和正式交付条件均未改动。

**结论：开发版页面已能导出已保存工程、分块上传到另一个 workspace、后台导入，并由操作者显式打开。** 验证限于自带小型 SHP 夹具和云端 Linux 浏览器冒烟，没有在 Windows `F:\MapFactory`、真实 0621 工程或独立地图工程师任务上验收。另外发现一个内核缺陷：从未启用编辑的工程不能导出（见第 4 节），本次未修。

## 1. HTTP 合同

路由在新模块 `mapforge/workbench/transfer_api.py`，由 `app.py` 挂载。每个工作台进程（即每个会话 token）对应一个 `TransferService`，第一次调用迁移接口时才建立；进程退出时关闭，之后迁移接口一律返回 `session-closed`。

| 方法与路径 | 请求 | 返回 |
| --- | --- | --- |
| `GET /api/transfers` | 无 | 用途、`source_included=false`、`recompute_required=true`、`formal_delivery=false`、包上限、分块大小、文件后缀 |
| `POST /api/transfers/exports` | 只能含 `project_id`、`base_revision`、`request_id` | 导出任务记录 |
| `GET /api/transfers/jobs/{job_id}` | 无 | 任务记录（导出或导入） |
| `GET /api/transfers/jobs/{job_id}/package` | 无 | ZIP 字节；`X-Content-SHA256`、`X-Mapforge-Purpose: SAVED_PROJECT_REQUIRES_IDENTICAL_SOURCE`、`Content-Disposition` |
| `POST /api/transfers/uploads` | 只能含 `name`、`size`、`sha256` | 上传记录 |
| `PUT /api/transfers/uploads/{upload_id}/chunks?offset=N` | 原始字节，`application/octet-stream`，每块不超过 4 MiB | 上传记录；字节收齐且 SHA256 一致时为 `sealed`，否则为 `failed` 并带错误码 |
| `GET /api/transfers/uploads/{upload_id}` | 无 | 上传记录 |
| `POST /api/transfers/imports` | 只能含 `upload_id`、`request_id` | 导入任务记录 |

**上传协议选原始字节 PUT。** 现有 JSON 请求上限是 64 KiB，如果改用 JSON/base64 小块，512 MiB 的包要一万多次请求，体积还要多出约三分之一。原始字节只对上面这一条 PUT 路由开放。中间件对它同样检查 Host、Origin、Bearer token 和 CSRF，类型必须是 `application/octet-stream`，声明长度和实际读取都不超过 `MAX_CHUNK_BYTES`。其他非 GET 请求仍然只收 64 KiB 以内的 JSON。

服务拒绝时返回 `{"detail": 中文原因, "code": 错误码}`：

- **404**：未知任务或上传，以及当前会话没有这个导出包；
- **409**：迁移忙、请求 ID 改了参数、会话已关闭、上传数量达上限、导出后工程或来源已变化；
- **507**：磁盘空间不足；
- **422**：其余（含请求字段不合规的 `invalid-transfer-request`）。

后台任务失败不走 HTTP 错误，而是在任务记录的 `error.code` / `error.message` 里说明，例如同 ID 工程已存在为 `project-already-exists`。

## 2. 页面行为

- 顶栏新增“工程迁移”按钮，对话框首段说明：包不含原始 SHP 与 Profile，导入方需同源原件，导入后旧候选和检查过期，迁移不是正式交付。
- **导出**：只发送当前工程 ID 和已保存修订。下载后核对字节数、响应头 SHA256 和浏览器自算 SHA256，三者一致才保存文件。有未确认的待办输入时先提示，这部分不会进入工程包。
- **导入**：只接受 `*.mapforge-project.zip`（服务端同样校验），超出包上限的不上传。浏览器先算整包 SHA256，再按服务端给的分块大小顺序上传。封存失败就停止，不发起导入。导入在后台运行，期间可以关闭对话框继续看当前工程；窗口关着时出了结果或失败，会在页面顶部提示。
- **打开**：导入成功后只刷新工程列表，并显示保留情况和需重算的内容，**不自动打开**。由操作者点“打开导入的工程”；如有未确认待办，会先确认是否放弃。不自动编译、接受候选或导出。
- 同一时间只允许一个迁移任务，进行中时导出、选文件和导入按钮都不可用。

## 4. 发现的缺陷：从未启用编辑的工程不能导出

`ProjectStore.create` 建立的工程，`context` 里 `compiler_hash`、`policy_hash` 是空字符串，要等启用边界编辑或来源重建、登记编译上下文后才会填上。迁移内核 `project_relocation._project` 对当前快照、`previous.json` 和历史原始快照都用 `validate_context` 严格要求四项完整 SHA-256。结果：

- 只有待办、从没启用过编辑的工程（例如六个转换失败的源工程）导出时任务失败，页面显示 `StoreValidation: compiler_hash: 需要小写 SHA-256（transfer-failed）`。原因如实显示了，但地图工程师看不懂。
- 已启用编辑的工程，只要上一版 `previous.json` 还是未绑定上下文的状态，同样失败；再保存一次之后才能导出。`scripts/workbench_relocate_project.py` 用的是同一内核，行为一样。
- 现有服务测试夹具都在建工程后马上登记能力，所以一直没暴露。

建议修法：在 `_project` 中允许 `context == context_for(source_snapshot)`（即 `store.create` 写入的未绑定状态），其余情况仍走严格校验，并补未绑定工程的导出、导入测试。本次没有修。搬迁回执会记录 `project_relocation.py` 的实现哈希（`implementation_sha256`），`out/workbench/surface-relocation-20261009/` 的证据很可能因此绑定这个文件；云端机器没有 `out/`，无法按 CLAUDE.md 的证据绑定规则核实影响。需要负责人确认后再改。
