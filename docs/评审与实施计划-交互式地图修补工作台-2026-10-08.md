2026-10-08。评审对象：[产品规划](产品规划-交互式地图修补工作台-2026-10-08.md)。用户已确定首批角色为地图工程师，优先通过页面完成导入、人工修补、检查和交付。

**结论：产品方向通过；实施范围按本次评审收窄。先做 IBD SHP 单路口工程与一种经实证可行的人工编辑工具。源工程和页面独立推进，几何探针不再阻塞所有界面工作。** 本文保留评审时的实施任务基线，评审时任务尚未执行；原规划描述目标体验，与本文冲突的首轮顺序、工具范围和工期以本文为准。

代码基线为 `main` / `17a22d2`，当前几何验证运行 `20261008-safe-mouth-recovery-v3`。本次评审阶段只读审查代码及既有运行产物，没有生成新地图或执行几何试验。用户随后已要求按方案持续实施至满足发布要求，实际完成项、候选与验证边界另见 [工作台实施记录](工作台实施记录-2026-10-08.md)；本文保留任务基线，不把任务定义本身当作完成证据。

## 1. 评审发现及处理决定

### R1 首个口部工具的可行性假设不成立，优先级 P1

原规划优先从两个短进口案例验证口部调整。代码核对后发现：

- `shp_mouth_envelope.convert(..., margin_m)` 及底层 `build_junction_xodr(..., mouth_margin_m)` 只接收一个全局标量，所有进口共用；没有按稳定口部身份覆盖参数的入口。[包装入口](../mapforge/ops/shp_mouth_envelope.py)、[生成器](../mapforge/ops/shp_to_xodr.py)
- 固定当前源链与原轴时，`_source_envelope_axis` 的保留站位随 margin 减小等量增加。`0701` 当前站位约 2.167 m，margin=3 m；降到零后也只有约 5.167 m，仍小于 6 m 保留下限。
- `0629` 当前站位约 138.917 m，保留下限约 150.503 m；降到零后约 141.917 m，仍差约 8.586 m。
- 这些是现有日志和公式推得的固定模型结论，不是新运行结果，也不能推导为一般几何无解。负 margin、删除保护或修改原件不作为解法。

处理决定：这两例先作为“源工程能打开 + 单 margin 无解能解释”的负例。口部工具进入后续结构编辑工作包；首个正向编辑优先检查普通道路共享边界的有限范围修形，具体对象必须经过 WB-04 的实证选择。不能将全局 margin 滑块伪装为局部口部编辑。

评审时正例尚未确定。只读取证发现 `0808` 的普通边界已达草案要求，其主要失败是连接路，不适合为了演示边界工具而硬选；`0801` 的 road12/lane−5、源 `2023080110475835655` 虽为单 Line 轴，但 XODR 来源记录标为 `lane-transition-taper`、`short-transition-stretched`。必须先查清事件域与源角色，不能把它直接当作普通非事件区正例。WB-04 将据此排除不适用区间或登记新的明确范围，不提前宣称修补可行。

证据：[0701 日志](../out/generalize/20261008-safe-mouth-recovery-v3/shp-2023070118182048481.convert.log)、[0629 日志](../out/generalize/20261008-safe-mouth-recovery-v3/shp-2023062913464138453.convert.log)。

### R2 草稿保存与应用候选的语义混合，优先级 P1

原规划允许保存不可编译意图，又说自动保存仅保存已应用操作。现有 `Project.apply` 必须有编译成功的 preview token，`save` 和 `reopen` 也调用 compile；直接沿用将使失败意图永远无法保存。[现有事务](../mapforge/repair_web/model.py)

处理决定：新工程区分“确认进入草稿的意图”和“接受编译结果”。结构、身份、单位及范围合法的意图可以进入待处理草稿；未通过编译不替换最后有效候选。未确认拖动和已取消操作不得自动落盘。具体状态契约见第 4 节。

### R3 源读取需保留原始身份和坐标，优先级 P1

`ProfileSource.lane/lanes_of` 等解释结果含推宽、推序号等派生行为，不能直接当原件真值；内部 `_m` 使用首次访问点作为局部原点，读取顺序不能决定客户工程的坐标系。[源引擎](../mapforge/adapters/shp/profile_source.py)

处理决定：首轮复用 `layer_raw_records`、`lane_raw_records`、`lane_boundary_records` 读取能力，以“源快照 + 图层 + 行号 + part”保留重复 ID、多部件和原字段；业务 ID 作为属性另存。工程坐标框架显式固定，原始值与派生解释分开。没有单位和框架证据时禁用米制编辑，不默认 WGS84。

### R4 首轮工具过多，且界面被求解依赖阻塞，优先级 P1

口部、长曲线、共享边界、连接路和面域的影响范围不同，不能在一个“首个闭环”任务里同时承诺。源查看、问题定位、保存草稿也不需要等待几何探针成功。

处理决定：首轮只开放一个具备能力声明的操作，其余工具不显示为可用。源工程线与几何验证线并行，真实预览在两线会合后接入。首个评估版本只承诺“已有生成结果上的一种人工修补 + 生成失败工程可打开保存”。“无 XODR 经人工修通”是下一道独立验收，保留为核心目标，不能提前声称完成。

### R5 交付依赖与估算缺乏任务级依据，优先级 P1

正式规格、绝对 CRS 和客户消费端若拖到最后一阶段，可能出现编辑器完成而没有一份可交付正例。原 7–11 周依赖未确认的人员投入和编辑编译适配难度，不能作为承诺排期。

处理决定：外部材料及用途规格从首周并行登记；只承诺首轮工作顺序和 10 个工作日的检查点，不承诺该检查点已经客户可用。WB-04/WB-05 完成后重估后续工期。每种首发声明的源格式/目标 Profile 都要有实际 DELIVERABLE 正例和阻断负例，缺少时仅评估版。

### R6 开发回归与客户任务验收需要分层，优先级 P2

14 份评分板、16 个泛化样本及两条编辑开发案例各有作用；两条演示链不能证明客户可独立工作。每次页面文案变化也没有必要运行数小时几何验证。

处理决定：按代码影响选择检查，几何发布仍完整回归；首个客户评估增加未参与开发的操作者和保留样本，记录实际人工时间、支持介入与失败原因。不得删除失败样本提高完成率。

## 2. 版本范围与三道验收

### V0 工程与受限编辑评估版

- IBD SHP、一个路口及关联道路、二维本地页面；支持已有结果作为基线，源导入不依赖 XODR。
- 选择/测量/原件叠图/问题定位、草稿保存重开、后台任务、一个经过 WB-04 证明的有限范围修补操作。
- 已生成结果中的真实残差可通过页面改善，输出带完整检查的研究候选；当前生成失败六例能查看原件、保存待办意图与明确原因。
- 不宣称已修通六个生成失败样本，不把历史 node4 七手柄演示作为新版本完成证据。

### V1 人工接管生成失败

- 对一个实际失败路口补齐源到候选的编辑编译入口，并完成必要口部/参考线/关联连接或面域工具。
- 在没有初始完整 XODR 的情况下，由地图工程师从源工程完成实际候选，经历保存重开、全范围检查及消费端读回。
- 一个样本成功后，用另一独立同类样本检验工具能力；其余失败逐类扩展，不能承诺任意拖动必有解。

### R1 限定范围正式发布

- 在 V0/V1 实际完成能力范围内定义支持清单，完成正式用途策略、CRS 等适用证据及指定消费端验收。
- 干净断网机器上有真实 DELIVERABLE 正例；材料缺失、失败和过期检查均不能正式导出。
- MAP 编辑、通用 Profile 编辑、三维编辑、跨路口编辑后置。MAP 源查看可另行并行，不增加首轮关键路径。

V0、V1 与 R1 是能力/验收阶段名称，不是已经发布的软件版本。现有自动转换默认行为、策略及原件保持基线。

## 4. 数据与接口合同

建议新增 `mapforge/workbench/` 承载 `sources`、`contracts`、`store`、`jobs`、`compiler`、`validation`、`api` 与本地静态页面；具体文件可按工作包合并，避免为了目录齐全先搭空框架。旧 `repair_web` 保持研究用途，不直接复用其固定 Project 初始化路径。

### 最小数据对象

- SourceSnapshot：源文件集合哈希、Profile 哈希、raw SourceRef、原字段/多部件、项目坐标框架及状态。未识别内容继续可追溯保存。
- Draft：schema 版本、project ID、revision、canonical content hash、对象解释和已确认 EditIntent、未解决问题。不要求存在 XODR。
- EditIntent：command ID、base revision、对象/源身份、操作类型、作用域、控制量及单位、允许影响集合。首轮不接受任意 XML 片段或任意 Python 表达式。
- Candidate：target draft content hash、源/编译器/Profile/策略哈希、实际文件哈希、影响集合、局部检查与失败清单。候选成功只表示编译状态，不代表 DELIVERABLE。
- ValidationBundle：所验候选及上下文指纹、检查范围、逐项结果、适用策略及最终裁决。换规则或源内容后旧结果只能作为历史。

### 操作语义

1. **preview**：对 base revision + 临时意图启动任务，不改变持久草稿；返回目标 draft hash。拖动中的几何虚影另标为未计算。
2. **commit draft**：校验命令结构、身份、单位/范围及版本后确认意图，产生新 revision；可以标为未解决/编译失败。未确认虚影与取消的意图不提交。
3. **accept candidate**：只接受当前草稿内容及源/工具指纹完全匹配的实际候选；迟到结果保留在历史，不改变当前状态。预览基于前一 revision 时以目标内容哈希精确对应，不因 revision 自增误用或误拒。
4. **save/reopen**：保存已确认草稿及事务，不运行 compile；编译失败可以保存。来源漂移时允许受限只读打开并解释缺失，不直接覆盖源绑定。
5. **undo/redo**：反转整个意图与派生关系事务，更新 revision 并使旧任务失效；内容相同的历史候选也必须重新核对完整指纹后才可复用。
6. **validate/export**：检查、封装和下载绑定同一不可变候选；原子完成包后才暴露下载。正式出口要求当前完整 ValidationBundle；缺结果、过期或失败不能靠客户端参数放行。

候选计算失败时，UI 同时显示当前待处理草稿和“上一成功候选，已过期”图层，不能把旧候选当新草稿的结果。只有确认进入草稿的操作自动保存；预览取消不产生隐藏历史。

任务接口至少包含 job_id、输入指纹、阶段、进度、错误对象和 terminal 状态。不能以退出码 0 或文件存在替代几何/交付状态。仅管理本服务启动的工作进程。

## 6. 验收与回归规则

### 必须覆盖的具体场景

- T01：16 个路口的源项目可建立；其中六个无完整 XODR 的项目能查看、定位、保存重开。
- T02：原始重复 ID、多 part、缺失引用和未知字段不丢失；读取顺序改变不改变项目坐标。
- T03：零编辑输出相同；一次非零真实修补改善预先指定的残差，原件和未编辑对象不发生未声明变化。
- T04：未确认拖动取消无历史；确认但不可编译的意图可保存重开，上一有效候选明确过期。
- T05：共享边界一次编辑影响相邻车道的派生宽度/中心，固定外边界及端口保持；UI 控制量与真实能力一致。
- T06：A/B 预览乱序、任务取消、重复请求、两个窗口并发、保存后旧结果到达，不得覆盖新状态或点亮正式导出。
- T07：保存/导出中断、磁盘不足、子进程崩溃、项目移动和源内容变化，保留上一完整事务并解释恢复路径。
- T08：真实浏览器完成编辑、撤销、重做、保存、重开、检查、候选导出；同一结果的画布/报告/文件一致。
- T09：没有 CRS 材料、必需检查失败、缺检查项或旧检查指纹时正式导出拒绝；工程仍可保存。
- T10：V1 必须有从无完整 XODR 到实际完整候选的人工任务；只打开失败页不能通过。
- T11：R1 每个宣称的源格式/目标 Profile 至少一个真实 DELIVERABLE 正例，另有阻断负例。正例是交付链最低证明，不能替代代表性样本集。

### 按改动影响运行验证

- 文档、静态文案或布局：链接/差异检查与真实浏览器布局验证，不重跑几何批次。
- 状态、存储、任务、API：针对 T02/T04/T06/T07/T09 的单元及集成测试，复用现有 UI 数学/时序回归；假任务只证明时序。
- 编辑算子或编译适配：先目标样本及来源/影响范围验证，阶段稳定后运行完整 14 份评分板与固定 16 个泛化对照。新编辑能力另跑操作用例，默认管道全绿不能替代它。
- 改几何的定版：沿用项目定版流程，完整默认生成、重评登记、前后全部指标对比和必要全量 pytest；代码在生成/评分过程中保持固定。仅 SHP 功能须验证 MAP 未变。
- 客户候选：独立操作者与未用于调试的样本，记录任务完成和研发介入；固定同机对照，不把跨机候选变化算成代码收益。

首轮需新建相应测试文件，已有 `tests/test_repair_workbench.py`、`tests/repair_ui_math.test.mjs` 只提供历史交互合同参考。用 `out/workbench/<运行名>/` 另存新证据，登记实际 source/code/policy/input hash；不覆盖旧研究目录，不改旧实验的 git.head。

范围外保持按稳定源身份与实际几何区间比较，不能只比较聚合分数。若编辑编译需要重编号或重序列化，则分别报告字节差异、身份映射与几何不变证明；不能凭“只是序列化”豁免未核对变化。无编辑路径仍要求同机基线字节一致。
